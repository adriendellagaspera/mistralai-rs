# Candidate Fern upstream issues

Prepared from the Mistral 288 spike. These are drafts only; do not publish without review.

## 1. Rust SDK: multipart/form-data + SSE generates non-compiling code

### Summary

A Rust endpoint with a multipart/form-data request body and an SSE response is emitted using `execute_multipart_request<T: DeserializeOwned>`, even though the generated endpoint return type is `SseStream<T>`.

### Observed result

For the Mistral audio transcription streaming endpoint, generated code effectively does:

```rust
pub async fn stream(...) -> Result<SseStream<TranscriptionStreamEvents>, ApiError> {
    self.http_client
        .execute_multipart_request(...)
        .await
}
```

`execute_multipart_request<T>` requires `T: DeserializeOwned`, so `cargo check` fails with E0277 because `SseStream<TranscriptionStreamEvents>` is not deserializable.

### Root cause

In `generators/rust/sdk/src/generators/SubClientGenerator.ts`, the `isFileUpload` branch distinguishes only:

- `responseType === "binary"` → `execute_multipart_stream_request`;
- everything else → `execute_multipart_request`.

The later SSE branch is only reached for non-file-upload endpoints.

### Expected

Multipart endpoints with `responseType === "sse"` should use a multipart SSE executor equivalent to `execute_sse_request`, preserving multipart body construction and SSE headers/parsing.

### Minimal fix direction

Add `execute_multipart_sse_request<T>` and select it when `isFileUpload && responseType === "sse"`. Add a generator fixture that must pass `cargo check`.

## 2. OpenAPI importer: `x-fern-sdk-group-name` is ignored without `x-fern-sdk-method-name`

### Summary

An operation-level `x-fern-sdk-group-name` has no effect unless `x-fern-sdk-method-name` is also provided.

### Root cause

`packages/cli/api-importers/openapi/openapi-ir-parser/src/openapi/v3/converters/operation/convertOperation.ts`:

```ts
function getSdkGroupAndMethod(...) {
    const sdkMethodName = getExtension<string>(operation, FernOpenAPIExtension.SDK_METHOD_NAME);
    const sdkGroupName = getExtension(operation, FernOpenAPIExtension.SDK_GROUP_NAME) ?? [];
    if (sdkMethodName != null) {
        ...
        return { groupName, methodName: sdkMethodName };
    }
    return undefined;
}
```

The group extension is therefore discarded when no method override is specified.

### Why this matters

A user may want to preserve Fern's inferred/default method naming while changing only the resource hierarchy. Today the only workaround is to duplicate an explicit method name on every operation, which can make the OpenAPI overlay large and can accidentally preserve raw operation IDs instead of Fern's better inferred names.

### Expected

`x-fern-sdk-group-name` should independently override grouping while retaining the default/inferred SDK method name when `x-fern-sdk-method-name` is absent.

### Suggested test

OpenAPI operation with:

```yaml
operationId: getThing
x-fern-sdk-group-name: [beta, things]
```

should produce a method under `client.beta.things` without requiring `x-fern-sdk-method-name`.

## 3. OpenAPI importer: inline generated type can collide with top-level schema and replace its identity

### Summary

An inline schema generated from a containing model/property name can collide with an existing `components.schemas` name. In the observed case, Fern silently assigned the same type ID/name to two semantically different schemas.

### Reproduction shape

Top-level component:

```yaml
components:
  schemas:
    JudgeOutput:
      type: object
      properties:
        analysis: { type: string }
        answer:
          anyOf:
            - { type: string }
            - { type: number }
      required: [analysis, answer]
```

Another model has an inline discriminated property:

```yaml
Judge:
  type: object
  properties:
    output:
      title: Output
      oneOf:
        - $ref: '#/components/schemas/JudgeClassificationOutput'
        - $ref: '#/components/schemas/JudgeRegressionOutput'
      discriminator:
        propertyName: type
```

Fern derives the inline name `JudgeOutput`, colliding with the top-level component.

### Observed result

The direct OpenAPI IR contained `types/JudgeOutput` as the discriminated classification/regression union, while endpoints whose OpenAPI response is `$ref: '#/components/schemas/JudgeOutput'` still referenced `JudgeOutput`.

Their autogenerated `{ analysis, answer }` response examples were then validated against the union and failed with:

```
Missing discriminant property ("type")
```

### Workaround

Set an explicit `x-fern-type-name` on the inline property, e.g. `JudgeOutputConfig`.

### Expected

Generated inline type names must not silently collide with existing semantic type identities. Prefer either deterministic collision disambiguation or a fail-closed collision error naming both source locations.

## 4. OpenAPI importer rejects intentional allOf property narrowing

### Summary

Fern rejects request schemas that use `allOf` to inherit a base object and intentionally narrow one inherited property in a child schema.

### Reproduction shape

```yaml
ConversationRequestBase:
  type: object
  properties:
    stream:
      type: boolean
      nullable: true

ConversationRequest:
  allOf:
    - $ref: '#/components/schemas/ConversationRequestBase'
    - type: object
      properties:
        stream:
          type: boolean
          const: false

ConversationStreamRequest:
  allOf:
    - $ref: '#/components/schemas/ConversationRequestBase'
    - type: object
      properties:
        stream:
          type: boolean
          const: true
```

### Observed

Fern reports a duplicate `stream` property rather than treating the child schema as a refinement/narrowing of the inherited property.

The Mistral spike needed to flatten six known request variants by applying parent properties and overlaying the child property.

### Expected

A compatible child constraint should be allowed to narrow an inherited property in `allOf`, or the importer should provide a precise unsupported-refinement error rather than a generic duplicate property error.

## 5. OpenAPI importer rejects a valid leading-hyphen enum default

### Summary

A query parameter whose enum contains a leading-hyphen string and uses that string as its default is rejected by Fern import.

### Reproduction shape

```yaml
- in: query
  name: order_by
  schema:
    type: string
    enum: [created, -created]
    default: -created
```

### Observed

Fern rejects the default even though it is one of the declared enum values.

The spike works around this by removing the default while preserving the enum values, which loses client-default semantics.

### Expected

A string default must be accepted when it exactly matches one of the declared string enum values, including values beginning with `-`.
